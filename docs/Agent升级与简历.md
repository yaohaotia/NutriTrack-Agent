# NutriTrack Agent 升级与简历表达

## 项目定位

建议名称：**NutriTrack：基于工具调用与知识检索的健康管理助手**。

保留饮食记录、健康分析、社区评论点赞和通知等业务，将新增能力聚焦到一条能演示、能解释的链路：用户提问 → 查询本人饮食数据 → 检索营养资料 → 生成有依据的回答 → 展示工具执行摘要和资料来源。

技术栈可写：**Java 21、Spring Boot 3、LangChain4j、Spring Security / JWT、MyBatis-Plus、MySQL、Vue 3、Element Plus、LLM Tool Calling、关键词检索增强生成**。LangChain4j 用于模型接入、类型化消息和工具规格；工具执行循环、身份校验与短期会话仍由业务层控制。Redis 是原系统验证码等功能的依赖；本次 Agent 的短期会话记忆保存在进程内存，不要写成 Redis 会话记忆。

## 面试时讲清楚这些问题

**为什么需要 Agent？**
原来是将问题和有限上下文直接发给模型。现在“查某天饮食”“汇总一周记录”“查营养资料”分别对应确定性工具，模型能根据任务选择工具，并基于返回结果继续调用或回答。业务数据处理与文本生成分开，既便于测试，也能限制权限。

**为什么没有直接使用 LangGraph 或多 Agent？**
当前任务只有几类只读工具，既有系统已经是 Java 后端。采用轻量循环能把工具协议、停止条件和错误恢复讲清楚，并避免为演示引入多套服务。未来任务确实出现稳定的多阶段分支时，再考虑工作流或多 Agent。

**引入 LangChain4j 后还自己写了什么？**
框架负责模型适配、请求 / 响应转换、类型化消息与工具规格，减少手工拼装和解析 Chat Completions 协议的代码。`AgentService` 仍负责轮次与时间预算、重复工具检测、执行结果聚合和证据检查；`AgentTools.execute()` 负责用户隔离、参数校验及业务查询。没有使用 AI Services 的代理自动循环，也不能说只用一个注解就完成了全部权限与编排。具体迁移映射见 [LangChain4j 重构说明](LangChain4j重构说明.md)。

**检索究竟怎么做？**
文档按页解析并切分为有重叠的文段，使用本地BGE中文模型计算512维向量，查询时结合BM25和精确余弦检索，通过RRF融合排序。Agent最多取得三条文段和来源位置；个人文档在检索前按用户筛选。初始语料仍较小，实际评测和未命中用例见 [RAG架构与评测](RAG架构与评测.md)。

**如何防止用户读取别人的记录？**
身份来自服务端认证后的 Principal，再映射到用户 ID；模型参数和客户端请求不能指定另一个用户。饮食工具始终使用该用户 ID；会话读取和删除也校验所有者。前端隐藏用户 ID 不是权限控制，权限检查必须在服务端执行。

**如何控制 Agent 成本与失败？**
限制模型迭代次数、工具调用次数、历史消息数量和查询区间，设置单次模型调用与总执行时间预算。工具错误作为受控结果处理，凭据缺失的演示模式与真实模式分别标注。没有实测时不对成本、延迟和成功率做数字承诺。

**你实际做了哪些验证？**
先对照 [架构与验收](Agent架构与验收.md) 中的测试记录回答，区分“单元测试通过”“前端构建通过”“本地完整业务链路演示通过”和“真实模型调用通过”。能够指向测试名称、失败用例及修复前后行为，比背诵提升比例更有说服力。

## 学习与迭代顺序

1. 跑通一个有记录的本人账号，演示查一天饮食、汇总一周、检索资料和连续追问；同时保留无记录场景。
2. 阅读 `AgentService`、`AgentTools`、`AgentMemory` 和模型客户端，能逐步解释一次请求如何进入、停止、失败以及保存上下文；分清哪些协议能力由 LangChain4j 提供、哪些业务控制仍由自己实现。
3. 完成越权会话、非法日期、未知工具、工具预算耗尽和模型超时的边界验证，记录真实结果。
4. 用真实模型整理一组固定问题，记录工具选择是否正确、数据是否忠实、来源是否相关、耗时和 token 用量。没有这些数据，简历不写效果提升比例。
5. 文档导入、本地向量和混合检索已实现；下一步扩大可靠语料，补充独立评测及回答忠实性检查。多实例共享会话、专用向量存储和重排仍属于后续计划。
